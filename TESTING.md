# Тестирование Context Optimizer v0.4

Это руководство — для первой пользовательской приёмки. Оно не требует Matreshka Agent.

**Начинайте не с рабочего production-проекта, а с копии проекта или небольшого тестового репозитория.**

## Что мы проверяем

Первая приёмка отвечает на шесть вопросов:

1. Навык корректно устанавливается в выбранное приложение.
2. Быстрая команда появляется и вызывается из чата.
3. Аудит выдаёт понятный русский отчёт и не выдумывает отсутствующие метрики.
4. Состояние сохраняется и читается в новом чате.
5. `optimize` сам ничего не меняет.
6. Подтверждаемое изменение и откат не затирают чужие правки.

Production-экономия токенов проверяется позже на сопоставимых реальных задачах.

---

## Этап 1. Подготовьте безопасный тестовый проект

Подойдёт:

- копия небольшого реального проекта;
- отдельная тестовая ветка;
- новый пустой репозиторий с несколькими файлами.

Перед началом убедитесь, что вы можете восстановить исходное состояние проекта.

В корне проекта полезно выполнить:

~~~bash
git status
~~~

Если там уже есть несохранённые изменения, запомните их или используйте отдельную копию.

---

## Этап 2. Проверьте Python

### Windows / PowerShell

~~~powershell
py -3 --version
~~~

### macOS / Linux

~~~bash
python3 --version
~~~

Нужен Python 3.11 или новее.

---

## Этап 3. Установите навык только в тестовый проект

Распакуйте пакет Context Optimizer в отдельную папку и откройте терминал **в папке пакета**, где находится `install.py`.

Сначала выполняется только preview.

### Codex

Windows:

~~~powershell
py -3 install.py install --host codex --project "C:\Projects\test-project"
~~~

macOS / Linux:

~~~bash
python3 install.py install --host codex --project "/path/to/test-project"
~~~

### Claude Code

Замените host:

~~~text
--host claude
~~~

### Cursor

~~~text
--host cursor
~~~

### Antigravity

~~~text
--host antigravity
~~~

Для Antigravity CLI:

~~~text
--host antigravity-cli
~~~

Preview покажет target и строку `INSTALL-...`. Проверьте путь и только после этого повторите ту же команду с:

~~~text
--approve "INSTALL-..."
~~~

Не придумывайте approval token вручную.

---

## Этап 4. Проверьте установку из терминала

Пример для Codex:

~~~bash
python3 install.py doctor --host codex --project "/path/to/test-project"
~~~

На Windows используйте `py -3`.

Ожидаемый результат:

- manifest найден;
- установленные файлы совпадают с контрольными суммами;
- нет сообщения о ручных изменениях внутри установленного skill.

---

## Этап 5. Проверьте быструю команду внутри приложения

Перезапустите приложение или обновите список skills.

### Codex

В чате:

~~~text
$context-optimizer help
~~~

Можно также открыть `/skills` и выбрать `context-optimizer`.

### Claude Code

~~~text
/context-optimizer help
~~~

### Cursor

~~~text
/context-optimizer help
~~~

### Antigravity

~~~text
/context-optimizer help
~~~

**PASS:** появляется русская справка по режимам и аудит сам не запускается.

Если команда не появилась, не меняйте разрешения приложения наугад. Сначала выполните `install.py doctor`, затем проверьте фактический каталог установки и версию приложения.

---

## Этап 6. Первый аудит существующего проекта

В чате приложения:

Codex:

~~~text
$context-optimizer adopt
~~~

Остальные:

~~~text
/context-optimizer adopt
~~~

Ожидается:

- отчёт на русском;
- найденные проблемы отделены от рекомендаций;
- bytes не называются токенами;
- неизвестные runtime-метрики показываются как неизвестные;
- в проекте появляется локальная папка `.context-optimizer/`;
- создаются Markdown/HTML/JSON отчёты и `STATE.md`.

Проверьте:

~~~text
.context-optimizer/STATE.md
.context-optimizer/latest.json
.context-optimizer/audits/
~~~

**Не коммитьте `.context-optimizer/` в Git.**

---

## Этап 7. Новый чат

Закройте текущий чат, создайте новый в том же проекте и вызовите:

~~~text
/context-optimizer status
~~~

или в Codex:

~~~text
$context-optimizer status
~~~

**PASS:** система читает уже сохранённое состояние и не делает вид, что это новый проект.

Затем:

~~~text
/context-optimizer resume
~~~

**PASS:** выполняется новая проверка, но исходный baseline не стирается без причины.

---

## Этап 8. Проверьте, что optimize ничего не меняет сам

~~~text
/context-optimizer optimize
~~~

Ожидается список приоритетных предложений.

Сразу после команды:

~~~bash
git status
~~~

**PASS:** исходный код и настройки проекта не изменились только из-за `optimize`.

---

## Этап 9. Проверьте память между чатами

Вызовите:

~~~text
/context-optimizer remember
~~~

Сначала система должна показать:

- целевой файл: `AGENTS.md`, `CLAUDE.md` или `GEMINI.md`;
- точный управляемый блок;
- MEMORY approval token.

**Не подтверждайте сразу.** Сначала убедитесь, что существующие правила проекта остаются нетронутыми.

После явного подтверждения система может записать только показанный управляемый блок.

Проверьте:

- старый текст не удалился;
- управляемый блок появился один раз;
- повторный `remember` не создаёт дубликаты.

---

## Этап 10. Тест одного безопасного изменения

Этот тест делайте только в копии проекта.

1. Выполните `optimize`.
2. Выберите одно небольшое обратимое предложение.
3. Попросите агента: **«Покажи dry-run этого изменения, ничего не применяй»**.
4. Агент должен показать:
   - файл;
   - точный diff или перенос;
   - finding `CTX-xxx`;
   - риск;
   - актуальный `APPLY-...` token.
5. Не подтверждайте изменение, если diff отличается от ожидаемого.
6. После явного подтверждения примените изменение.
7. Сразу проверьте `git diff`.

**PASS:** изменилось только то, что было показано в dry-run.

Если после apply вы вручную измените тот же файл, автоматический rollback должен отказаться затирать ваши новые правки.

---

## Этап 11. Проверка эффекта

Полный PASS эффективности требует сопоставимой задачи **до** и **после** изменения:

- тот же тип задачи;
- тот же provider;
- та же модель;
- одинаковая семантика token metric;
- task success не хуже;
- retries/errors/wrong-file reads не выросли;
- information loss = NO.

Результаты:

~~~text
VERIFIED_KEEP
NEEDS_MORE_DATA
ROLLBACK_RECOMMENDED
~~~

`NEEDS_MORE_DATA` — нормальный результат. Его нельзя повышать до PASS по уменьшению размера файлов.

Если получен `ROLLBACK_RECOMMENDED`, откат **не выполняется автоматически**. Система сначала должна показать актуальный `ROLLBACK-...` token.

---

## Этап 12. Завершение сессии

Перед окончанием теста:

~~~text
/context-optimizer finish
~~~

или:

~~~text
$context-optimizer finish
~~~

**PASS:** сохраняется итог сессии. Если нет сопоставимых runtime before/after данных, система прямо сообщает, что экономия токенов не подтверждена.

Автоматического запуска `finish` при закрытии окна пока нет.

---

## Этап 13. Обновление и удаление

Проверьте `update` на тестовой установке:

1. preview;
2. approval;
3. `doctor`;
4. skill по-прежнему вызывается.

Затем `uninstall`:

1. preview;
2. approval;
3. active skill удалён;
4. сохранённые аудиты проекта и project instruction files не удалены.

## Что прислать при ошибке

Не присылайте пароли, API keys или приватный полный transcript.

Достаточно:

1. приложение и версия;
2. ОС;
3. project/user scope;
4. какая команда вызвана;
5. полный текст ошибки без секретов;
6. вывод `install.py doctor`;
7. какой режим: help/adopt/resume/...;
8. если проблема с отчётом — его раздел «Ограничения», а не весь raw transcript.

Для воспроизводимости полезно также указать commit из `PACKAGE-MANIFEST.json`.

---

## Когда считать пользовательскую приёмку успешной

Первая приёмка v0.4 считается успешной, если:

- установка и удаление не затрагивают чужие файлы;
- команда появляется хотя бы в фактически используемых вами host-приложениях;
- аудит автономно создаёт понятный отчёт;
- новый чат восстанавливает состояние;
- optimize не меняет проект сам;
- remember требует отдельного подтверждения;
- одно тестовое изменение совпадает с dry-run;
- rollback не затирает post-apply edits;
- отсутствие runtime данных остаётся UNKNOWN/UNVERIFIED;
- никаких неожиданных фоновых установок, hooks или сетевых отправок нет.

После этого можно переходить к production before/after измерениям на реальных задачах.
